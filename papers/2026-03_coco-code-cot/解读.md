# 大白话深读《CoCo: Code-as-CoT》

## 1. 30 秒定位

这篇论文解决的核心问题是：统一多模态模型（Unified Multimodal Model, UMM）在生成结构化图像（如图表、数学图、带密集文字的海报）时，自然语言形式的思维链（Chain-of-Thought, CoT）太抽象，无法精确指定空间布局、文字内容和结构关系。作者提出 CoCo（Code-as-CoT），把推理过程直接写成可执行的 Python 代码，代码在沙盒中运行生成确定的“草稿图”（draft image），模型再以草稿为视觉脚手架做精细编辑，输出最终高保真图。论文在 Bagel 基座上构建了 CoCo-10K 数据集，包含文本-代码对和文本-草稿-终图三元组。在 StructT2IBench 上总体准确率 73.52%，比最强对照 GPT-Image 的 49.58% 高约 23.94 个百分点（Table 1）；在 OneIG-Bench 文本渲染子集总体 0.853，LongText-Bench 总体 0.754，均显著超过 Bagel 原模型（OneIG 0.305，LongText 0.342，Table 2）。论文用实验证明：少量代码监督（5% 比例）即可诱导出可执行推理，100% 编译成功（320/320），而原始 Bagel 只有 9.1% 编译成功（29/320，Fig. 7）。核心观点是：可执行代码比自然语言更适合作为视觉生成的中间表示。摘要还给出相对直接生成的增益为 +68.83%、+54.8%、+41.23%，分别对应三个基准（Abstract）。

## 2. 为什么这篇论文会出现

统一多模态模型把视觉理解与生成合并在一个架构里，但生成侧性能长期落后于专用扩散模型，尤其在结构化视觉和密集文本渲染上。Bagel、Janus、Emu3 等模型能处理图文交错输入，却很难直接生成正确坐标轴、图例、公式标签或海报文字（§1）。最近的 CoT 方法试图把推理引入生成，例如 Image-Gen-CoT 用奖励模型在早期解码步骤评估生成质量，Bagel-Think 在生成前置文本推理，但这些方法依赖自然语言计划。自然语言无法精确表达“y=x² 抛物线顶点在 (0,0)，红色直线 y=-x 经过原点，虚线辅助线相交于 P 点，区域 A、B 标注”这类结构化意图（§1，Fig. 1）。作者在引言中明确举例：模型常把“2D plot of y = x²”生成错误结构或不可辨认文字，因为缺少显式视觉 grounding。

另一方面，代码天然适合描述布局和文本：`ax.text(512, 675, "开启您的星际探险之旅", fontsize=38)` 直接给出坐标、字符串、字号；`ax.add_patch(...)` 指定几何形状、颜色和透明度（Fig. 5）。代码执行后得到的草稿图使推理结果可观察、可验证。这比文字 CoT 更接近“思维外化”。但现有数据集既没有代码生成监督，也没有草稿到终图的细粒度修正信号。作者观察到 Bagel 零样本生成的代码大多不可执行，且模型会忽略草稿语义重新生成新图（§3.3.1）。零样本试点研究揭示两个关键局限：第一，Bagel 能产出代码，但生成代码经常不可执行，导致低质量输出；第二，模型倾向于忽略草稿语义而直接生成全新图像，使草稿失去意义。因此需要构造 CoCo-10K，同时教会模型“写可执行代码”和“根据草稿做保留结构的精修”。论文动机可归纳为三句话：统一模型生成结构化图像能力差；自然语言 CoT 精度不足；代码可作为精确、可验证的中间推理表示，但缺数据。

## 3. 读懂前需要的最小概念

**统一多模态模型（UMM）**：用单一网络同时处理图像理解（图像→文本）和图像生成（文本→图像）。Bagel 采用混合架构：SigLIP ViT 编码器负责理解侧视觉 token，VAE 编码器负责生成侧视觉 token，然后用 Mixture-of-Transformer-Experts（两分支 Transformer）分别处理这两类 token。文本 token 与视觉 token 在序列中交织，模型自回归预测下一个 token（§3.1）。理解任务中，输入图像经 ViT 编码为视觉 token 序列，Transformer 自回归预测文本 token；生成任务中，Bagel 采用 Rectified Flow 将 VAE token 解码为高保真图像。

**思维链（CoT）**：让模型在给出最终答案前先生成中间推理步骤。在文生图里，CoT 可以是文本计划、图像草稿或多轮交互。CoCo 的 CoT 是可执行代码。传统文本 CoT 依赖自然语言描述，无法精确指定空间约束；代码 CoT 将推理过程表示为可执行的 Python 脚本，直接编码布局、文字内容和对象关系。

**代码执行沙盒**：受限的隔离运行环境，模型生成的 Python 代码在其中运行，输出图像文件。沙盒限制文件系统、网络、系统调用，保证安全（§3.2）。论文明确说明沙盒通过受限操作和隔离运行时环境确保安全稳定执行。

**草稿-精修（draft-refine）范式**：先生成低质量但结构正确的草稿，再以草稿为条件生成高质量终图。草稿的作用是提供确定性的视觉骨架，降低一次性生成的难度。代码渲染出的草稿虽然视觉上简单，但能够忠实反映代码指定的对象位置、文本内容和结构关系。

**VAE 与 Rectified Flow**：VAE 将图像压缩到潜空间 token 序列；生成时模型输出 VAE token，再用 Rectified Flow（整流流）解码为像素图。Bagel 用 Rectified Flow 解码 VAE token 得到高保真图（§3.1）。训练时通过线性插值 \(x_t = (1-t)x_0 + t x_1\) 构造带噪潜变量，模型学习预测速度场。

**Text-Code 对与 Text-Draft-Final 三元组**：CoCo-10K 的两种训练格式。前者教模型从提示词生成可执行代码；后者教模型把代码渲染出的草稿图精修为语义一致的终图（§3.3.3）。三元组中 Text-Draft-Final 配对监督使模型学习草稿构建和草稿引导精修两个阶段。

**三个原子修正能力**：CoCo-10K 围绕三个原子修正能力构建：通用编辑（general editing）、科学图表（scientific diagrams）和复杂文本（complex text）。每个能力都有专门的数据合成管线（§3.3）。

## 4. 方法全景：先看数据流

CoCo 的推理数据流如下：

```
输入提示词 p
   │
   ▼
[Unified MLLM: 代码生成阶段] ──► 可执行 Python 代码 c
   │
   ▼
[沙盒环境执行] ──► 确定性草稿图 I_d （结构化布局、文字、几何形状）
   │
   ▼
[ViT 编码器 + VAE 编码器] ──► 草稿的语义特征 + 潜空间细节特征
   │
   ▼
[Unified MLLM: 精修阶段] ──► 最终高保真图像 I_f
```

训练时的数据流略有不同：CoCo-10K 提供 `(p, code, I_d, I_f)` 或 `(p, code)` 两种序列。对于 Text-Draft-Final 三元组，输入序列为提示词 token、草稿图 ViT 特征、验证 token（原文写 “verifications”，论文未详细说明具体格式）、最终图像的噪声 VAE token；模型需要预测代码 token 和最终 VAE token。损失只在代码 token 上计算交叉熵，在最终图像 VAE token 上计算 MSE（§3.4）。训练阶段 1 是文本到代码微调，阶段 2 是全参数微调 16K 步；优化器设置未在论文中明确给出，仅给出学习率 \(2 \times 10^{-5}\) 和 2K warmup 步，以及 8 张 H800 GPU。训练时冻结 ViT 编码器、VAE 编码器及其 connector（§4.1）。

核心组件拆解：

1. **代码生成模块**：输入文本提示词 p，输出可执行 Python 代码 c。目的是把自然语言意图转换为确定性的布局规范。假设：模型具备基本的代码生成能力，且代码可以无歧义地表达场景的关键结构。代码只描述核心语义，不负责风格细节。可视化示例（Fig. 5）展示代码包含 `ax.text`、`ax.add_patch`、`patches.Rectangle`、`patches.Ellipse`、`FancyBboxPatch` 等 matplotlib/seaborn 调用，用来精确指定文本位置、几何形状、颜色和透明度。

2. **沙盒渲染器**：输入代码 c，输出草稿图 I_d。目的是把代码执行成具体视觉表示。假设：运行环境稳定安全，代码渲染出的草稿能忠实反映代码中指定的位置、文字、几何关系。草稿视觉质量粗糙，但结构准确。CoCo-10K 的 Fig. 5 展示了草稿图往往是色块、几何形状和文字组成的基础可视化，缺少真实纹理和光影。

3. **草稿引导精修模块**：输入草稿图 I_d 和原始提示词 p，输出最终图 I_f。目的是在保持草稿结构的前提下提升视觉保真度和真实感。Bagel 中草稿同时经 ViT 和 VAE 编码：ViT 提取高层语义特征供全局推理，VAE 保留低级视觉细节供精确编辑（§3.2）。假设：模型能够选择性编辑，即保留正确结构、纠正错误元素。Fig. 3 展示同一个草稿图和精修后的终图在结构上保持一致，但终图增加了真实纹理、光影和细节。

4. **CoCo-10K 数据集**：Editing Dataset 用 StructVisuals 中的 A-Image（原始图）和 B-Image（修正图）训练结构感知和精确修正；Synthesis Dataset 用 Gemini-3-Pro 生成代码，沙盒渲染为 A-Image，再用 Nano Banana 精修为 B-Image，得到三元组。两个子集分别保障“会看结构”和“会生成结构”（§3.3.2）。Fig. 4 显示 Editing Dataset 下分通用编辑和科学图表，各约 2.5K；Synthesis Dataset 下分科学图表和复杂文本，合计约 4K；另有 1K 复杂文本类样本，总规模超过 10K（论文写超过 10K 结构化监督实例，§3.3.1）。

方法的关键设计是**把推理外化为可执行的中间产物**，而不是内部隐式 CoT。草稿图是代码执行的结果，因此推理的中间步骤可验证、可检查。与 IRG 的多轮“文→图→文→图”迭代不同，CoCo 采用的是先代码后精修的两阶段流程，代码显式提供布局和约束，使生成过程确定性更强。

## 5. 核心公式与直觉

论文只给出两个训练损失，公式简单但足以理解训练目标。

**公式（1）：代码生成损失**

\[
\mathcal{L}_{\text{code}} = -\frac{1}{|v|}\sum_{i=1}^{|v|}\log(v_i)
\]

其中 \(v_i\) 是模型在位置 \(i\) 预测的代码 token 概率分布中对真实 token 的取值。这是标准的 token 级交叉熵（Cross Entropy）损失，用于监督自回归代码生成。直觉：模型每步都要最大化真实代码 token 的概率。工程对应：在训练序列中，只有代码片段的 token 参与 \(\mathcal{L}_{\text{code}}\)，提示词和图像 token 不参与。\(|v|\) 是代码 token 序列长度。该损失直接对齐自回归语言建模的常规做法，与 LLM 预训练/微调一致。

**公式（2）：最终图像潜空间损失**

\[
\mathcal{L}_{\text{final image}} = \mathbb{E}_{t,x_0,x_1}\left[\|m(t, x_t) - (x_1 - x_0)\|^2\right]
\]

这是 Rectified Flow 的 MSE 损失。变量解释：\(x_0\) 是初始噪声潜变量，\(x_1\) 是目标干净潜变量，\(t\in[0,1]\) 是时间步，\(x_t = (1-t)x_0 + t x_1\) 是线性插值后的带噪潜变量，\(m(t, x_t)\) 是模型预测的速度场（velocity）。优化动作：让模型预测的速度场逼近真实速度 \(x_1 - x_0\)。工程对应：训练时对最终图像 VAE token 做前向扩散采样 \(t\)，计算 \(x_t\)，模型输出 \(m\)，与目标速度做 MSE。这在 Bagel 中是标准生成损失（§3.1）。注意该损失是在潜空间计算的，即 VAE token 对应的潜变量，不是像素空间。

两个损失联合优化，但没有在论文中给出权重。从训练策略看，\(\mathcal{L}_{\text{code}}\) 只作用于代码 token，\(\mathcal{L}_{\text{final image}}\) 只作用于最终图像的 VAE token，因此是分开监督。公式虽然没有多复杂，但奠定了 CoCo 的两个可学习模块：代码生成和草稿精修。

另外论文中 Table 3 提出训练混合比例 \(r_c\)（Text-Code 对占的比例）。但没有公式化描述混合采样方式，仅说训练时混合两种数据源。实验发现 \(r_c=0.05\) 最优，说明少量代码监督足以诱导结构化推理，主导信号应来自草稿到终图的精修数据。关键消融在三组 \(r_c\) 上展开：\(r_c = 0.20\) 时英文 0.724、中文 0.667；\(r_c = 0.10\) 时英文 0.733、中文 0.671；\(r_c = 0.05\) 时英文 0.755、中文 0.753（Table 3）。这表明随着代码监督比例降低，中英文渲染性能持续提升，\(r_c=0.05\) 最优。这一反直觉现象可以解释为：模型从少量 Text-Code 对即可学会代码语法和可执行性，而大量精修三元组才是提升文本渲染精度的主力；过高的代码监督可能会挤占草稿精修能力的训练容量。

## 6. 训练到底怎么跑

CoCo 从 Bagel 基座做监督微调（SFT），训练分两个阶段。

**阶段一：文本到代码微调。** 因为观察显示 Bagel 很不会生成可执行代码，作者先进行一轮 text-to-code 的 fine-tuning，赋予模型基本的代码生成能力（§4.1）。论文未披露该阶段的具体步数、学习率或数据规模，但可推断使用 CoCo-10K 中的 Text-Code 对。这一阶段的动机来自零样本试点：原始 Bagel 在 LongText-Bench 上只有 9.1%（29/320）的代码编译成功率（Fig. 7）。该阶段的目标是让模型具备可执行语法，为后续联合训练提供稳定的代码输出。

**阶段二：全参数微调 16K 步。** 混合使用 CoCo-10K 和 StructVisuals 数据集，同时加入 StructVisuals 的 caption 标注以保留视觉感知能力。学习率 \(2\times10^{-5}\)，2K warmup 步。冻结 ViT 编码器、VAE 编码器及其 connector，保证视觉编码和重建能力稳定。训练用 8 张 H800 GPU。训练后采用 EMA（指数滑动平均）权重做评估。

**一轮训练 step 的具体流程**（基于 §3.4 和 §3.3.3）：

1. 从混合数据中采样一个样本。如果是 Text-Draft-Final 三元组，则准备提示词、草稿图和终图；如果是 Text-Code 对，则可能只有提示词和代码。
2. 草稿图通过 ViT 编码器得到视觉语义 token，终图通过 VAE 编码器得到干净潜变量。
3. 构建输入序列：`[提示词 token] [草稿 ViT token] [验证 token（论文未明确定义）] [噪声终图 VAE token]`。其中“verifications”在原文 §3.4 出现一次，可能指中间确认符号，具体格式未披露。
4. 前向传播：模型自回归预测后续 token。对于代码片段，计算交叉熵 \(\mathcal{L}_{\text{code}}\)；对于终图 VAE token，使用 Rectified Flow 目标计算 MSE \(\mathcal{L}_{\text{final image}}\)。
5. 反向传播更新参数（除冻结模块外）。重复 16K 步。

数据混合比例 \(r_c\) 是关键超参数，从 0.20 降到 0.05 时性能持续提升，最优 \(r_c=0.05\)。这意味着训练时 95% 样本是 Text-Draft-Final 三元组（精修任务），只有 5% 是 Text-Code 对。这很反直觉：代码生成能力不需要大量显式监督，少量代码对即可学会写可执行代码，而大量精修数据能更好地教会模型利用草稿。训练采用 EMA 权重进行评估，且未使用强化学习，完全是监督微调范式。论文也提到使用 StructVisuals 的 caption 标注来保护视觉感知能力，这属于理解侧的正则化。论文未披露批大小、梯度累积、优化器类型、混合精度等具体配置，因此无法估算单步实际显存和时间；但 16K 步在 8 张 H800 上属于中等规模微调，成本可控。

## 7. 推理到底怎么跑

推理时不需要训练数据或梯度，完整流程如下（§3.2）：

1. **输入提示词**。用户给一个文本 prompt \(p\)，例如“Travel agency advertisement features ‘Discover Your Next Adventure’…”。
2. **代码生成**。统一 MLLM 自回归生成 Python 代码 \(c\)。代码中显式包含画布尺寸、坐标、文字内容、几何形状等。Fig. 5 中展示代码指定了 `figsize`、`ax.text`、`ax.add_patch` 等参数。
3. **沙盒执行**。将代码 \(c\) 送入沙盒环境运行，输出草稿图 \(I_d\)。这一步是确定性的：相同代码产生相同草稿。沙盒提供受限操作和隔离运行时，保证安全。
4. **草稿编码**。草稿图 \(I_d\) 同时经过 ViT 编码器和 VAE 编码器。ViT 提供高层语义 token，VAE 提供底层潜空间表示。两个编码器分别服务于全局推理和精细编辑。
5. **精修生成**。将原始提示词 token、草稿 ViT token、草稿 VAE token 等组织成输入序列，模型自回归预测最终图像的 VAE token。预测完成后通过 Rectified Flow 解码器得到最终图像 \(I_f\)。

观察论文 Fig. 6 可知，推理时生成的代码并非固定 1024 分辨率，而是根据提示词动态配置画布宽高比（如海报用 16:9，图表用方形）。论文指出这是模型把画布参数视为推理过程的一部分（§4.4），不是记忆固定配置。Fig. 6 展示了同一模型生成的不同宽高比输出：旅游宣传海报采用宽幅，数学图表采用方形或近方形画布。

推理中的关键顺序是**先代码、后草稿、再精修**，不能跳过草稿直接生成终图。如果代码编译失败，流程中断；论文报告 CoCo 在 LongText-Bench 上 320/320 编译成功（100%），原始 Bagel 只有 29/320（9.1%）（Fig. 7）。因此推理可靠性高度依赖代码生成模块被训练过。Fig. 7 还展示了成功率和失败率：Baseline 成功 29 次、失败 291 次；CoCo 成功 320 次、失败 0 次，且有 95% 置信区间标注。推理流程不涉及迭代多轮，一次代码生成、一次草稿渲染、一次精修完成；这也与§2 中与 IRG 的“事后多轮精修”形成对比。与训练时不同的是，推理时不会使用最终图像 VAE token 作为目标，而是用 Rectified Flow 的解码器从预测的潜变量逐步采样得到像素图；论文没有披露推理采样步数，但可推断沿用 Bagel 的 Rectified Flow 采样流程。

## 8. 实验和消融到底证明了什么

主要结果如表 1、表 2 所示。表 1 是 StructT2IBench 上的准确率（%），表 2 是 OneIG-Bench 和 LongText-Bench 的文本渲染准确率。数据集规模：StructT2IBench 包含 1,714 个评估样本和 37,941 个 QA 对；LongText-Bench 包含 160 个提示词，覆盖 8 个场景，针对长中英文文本渲染；OneIG-Bench 文本渲染子集覆盖英文和中文任务，采用复合指标（编辑距离 + 完成率 + 词准确率）（§4.1）。评估协议：StructT2IBench 和 LongText-Bench 每个 prompt 生成一张图，OneIG-Bench 每个 prompt 生成四张图（§4.1）。

以下抽取 5 条关键证据：

| 证据 | 任务/数据集/指标 | CoCo 结果 | 对照方法结果 | 结论 | 锚点 |
|---|---|---|---|---|---|
| 结构化整体领先 | StructT2IBench Overall Accuracy | 73.52 | GPT-Image 49.58；Qwen-Image 41.03；Bagel 4.69 | 提升约 23.94 个百分点，大幅超过专用 T2I 模型 | Table 1 |

| 长文本渲染 | LongText-Bench Overall (EN+CN) | 0.754 | GPT-4o 0.788（英文 0.956 但中文 0.619）；Bagel 0.342 | CoCo 中英文均衡 0.755/0.753，优于 Bagel 极多，落后 GPT-4o 总体 | Table 2 |

表 1 的结构化任务中，CoCo 在 Graph 得 62.58（对照最高 57.00，来自 GPT-Image）、Math 得 69.12（对照最高 64.81，来自 Nano Banana）、Table 得 79.15（对照最高 83.31，来自 GPT-Image，CoCo 略低）、Puzzle 得 49.10（对照最高 63.87，来自 Nano Banana，CoCo 较低）。可以看到 CoCo 并非在每个子任务都第一：Puzzle 落后 Nano Banana 和 GPT-Image，Table 落后 GPT-Image。但总体平均高，主要靠 Chart、Graph、Math 和 Table 的大幅领先。表 2 中，OneIG-Bench 的对比方法包含生成专用模型 FLUX.1-dev、HiDream-I1、Kolors 2.0，统一模型 Janus-Pro、BLIP3-o、OmniGen2、Show-o2、BAGEL，CoT 方法 BAGEL-thinking，以及闭源 GPT-4o。CoCo 英文 0.895 超过 GPT-4o 的 0.857，中文 0.811 超过 GPT-4o 的 0.650；在 LongText-Bench 上，GPT-4o 英文 0.956 明显高于 CoCo 的 0.755，但中文 0.619 低于 CoCo 的 0.753，导致总体相近（0.788 vs 0.754）。这提醒我们：CoCo 在结构化文本渲染上很强，但纯长文本英文渲染仍有差距，可能受限于 VAE 潜空间对英文字形的压缩。

**最关键消融**：训练混合比例 \(r_c\)（Text-Code 比例）从 0.20 降到 0.05，LongText-Bench 英文从 0.724/0.667 提升到 0.755/0.753（Table 3）。这说明两点：第一，代码监督不是越多越好，5% 的代码对已足够教会模型写可执行代码；第二，草稿到终图的精修数据才是提升文本渲染精度的主要驱动力。作者解释：过高的代码监督会让模型把注意力过多放在代码生成，挤占了精修能力的训练。

另一个关键诊断是 Fig. 7 的代码可执行性：在 LongText-Bench 上，未经 CoCo 训练的 Bagel 代码编译成功率仅 9.1%（29/320），而 CoCo 达到 100%（320/320）。这直接支持了“Text-Code 监督不可少”的结论，也解释了为什么需要阶段一的 text-to-code 预微调。

**尚未证明的主张**：

- CoCo 在通用自然场景生成（非结构化、非文字密集）上是否同样有益，论文未给出结果。
- CoCo-10K 只有约 10K 样本，且依赖 Gemini-3-Pro 和 Nano Banana 合成，其分布偏差未分析。
- 精修阶段是否会过度依赖草稿，导致创意受限或无法摆脱代码错误，论文未做失败案例分析。
- 指标本身：StructT2IBench 用 QA 准确率，LongText/OneIG 用编辑距离等复合指标，这些指标未必完全反映人类对视觉美学或语义自然的判断。
- 消融未单独分析冻结 ViT/VAE 带来的影响，也未对比是否该冻结。
- 未展示代码-草稿-终图链路的端到端错误传播分析，例如某类代码错误是否会被精修模型纠正或放大。

## 9. 与前作怎么选

**CoCo vs. Bagel-Think（文本 CoT）**：Bagel-Think 在生成前置文本推理。优点是实现简单，不引入外部工具；缺点是自然语言无法精确表达布局。论文表 1 显示 Bagel-Think 在 StructT2IBench 总体只 9.03%，远低于 CoCo 的 73.52%；表 2 中 BAGEL-thinking 在 OneIG-Bench 总体 0.074、LongText-Bench 总体 0.087，远低于 CoCo 的 0.853 和 0.754。**选 CoCo** 当任务需要精确空间、图表、密集文字；**选 Bagel-Think** 当没有沙盒执行环境，或任务对结构精度要求不高，且希望保持端到端简洁。

**CoCo vs. IRG（Interleaving Reasoning Generation）**：IRG 采用多轮“文→图→文→图”迭代精修，通过视觉反馈改进输出。CoCo 是先代码后精修的两阶段，不涉及多轮文本反馈。IRG 更通用，可能适应更开放的创意生成；CoCo 的代码草稿提供确定性和可验证性，适合结构化任务。**选 CoCo** 当瓶颈在精确布局和文本渲染；**选 IRG** 当需要逐步调整生成结果且没有代码基础，或任务不适合代码描述（如抽象艺术）。

**CoCo vs. Qwen-Image、GPT-Image 等专用生成模型**：这些模型并非 CoT 方法，但可作为性能对照。GPT-Image 在 StructT2IBench 上 49.58，低于 CoCo 的 73.52；但 GPT-4o 在 LongText-Bench 英文 0.956，高于 CoCo 的 0.755。CoCo 在结构化任务上超过闭源 GPT-Image 约 24 个百分点，但在长文本英文渲染上仍落后 GPT-4o 约 0.2。**选 CoCo** 当需要开源、可本地部署且结构化生成更强；**选 GPT-4o** 当追求绝对文本渲染精度且可接受闭源 API。

**CoCo vs. Image-Gen-CoT**：后者用奖励模型在解码早期评估质量，本质是把生成模型退化为纯图像生成器。CoCo 采用显式代码草稿，可解释性更强。**选 CoCo** 当需要可执行中间产物；**选 Image-Gen-CoT** 当不希望改变输入模态或缺少代码执行环境。

## 10. 工程判断：可行性、风险与上限

**可行性**：CoCo 不改变模型架构，只增加数据流和训练目标，工程实现相对直接。需要维护一个安全沙盒（如受限 Docker + matplotlib/seaborn 环境）。训练成本：8 张 H800，16K 步，学习率 2e-5，对多数实验室可承受。论文未披露批大小、梯度累积、混合精度、训练时长等具体训练配置，需要外部推测。推理成本：额外增加代码生成和沙盒执行时间，以及草稿编码和精修前向，延迟肯定高于直接生成，但论文未披露具体延迟数据。

**数据风险**：CoCo-10K 仅约 10K 样本，其中 Synthesis Dataset 依赖两个商业模型（Gemini-3-Pro 和 Nano Banana），数据分布可能偏向这些模型的审美和代码风格。Editing Dataset 来自 StructVisuals，主要覆盖图表和结构化图像。因此模型可能对结构化任务过拟合，对开放域自然场景泛化未知。Fig. 4 中数据合成管线完全依赖外部模型，如果 Gemini-3-Pro 生成的代码质量下降或 Nano Banana 精修效果不稳定，数据集质量会直接受影响。此外，训练数据固定 1024 分辨率，但推理时模型会动态配置画布宽高比，这种训练-推理不一致可能引入未知风险。

**实现难点**：

1. **代码可执行性**：原始 Bagel 只有 9.1% 编译成功率，说明需要专门 text-to-code 预微调阶段。若代码依赖库版本变化或沙盒环境不匹配，编译可能失败。论文训练数据固定 1024 分辨率，推理时模型会动态配置画布，这种训练-推理不一致可能导致部分代码无法正确执行。
2. **草稿语义保持**：模型容易忽略草稿重新生成，这是论文的动机之一（§3.3.1 零样本试点）。训练需要大量精修三元组来强制对齐。
3. **画布动态化**：推理时模型可改变宽高比，但训练数据固定 1024，可能导致训练-推理分布漂移。论文§4.4 承认所有训练数据都构建在 1024 分辨率，但推理代码不限于此。
4. **外部工具耦合**：沙盒必须安装 matplotlib、seaborn 等库，版本需要与代码生成匹配；如果模型生成其他库的代码，执行环境可能不支持。

**失败环节**：最脆弱的是代码执行。如果用户提示包含代码无法表达的概念（如“梦幻光影”“情感氛围”），模型可能写出低质量代码，草稿无法携带有效结构信息。另外，精修模型可能对草稿错误过于保守，无法纠正代码中的错误（例如草稿中文文字写错，精修可能保留错误）。Fig. 5 展示了草稿中的文字渲染是可读的，但如果代码本身指定了错误文字，精修能否纠正仍不明确。

**监控信号**：应监控代码编译成功率、草稿渲染覆盖率（检测文字是否完整、几何是否正确）、精修前后语义一致性（CLIP 分数）、终图文本编辑距离。这些指标能提前发现训练退化。Fig. 7 的编译成功率是一个直接的监控信号，论文没有讨论其他信号。

**指标上限与未回答问题**：

- StructT2IBench 的 QA 准确率上限未必是 100%，因为 QA 本身可能不完美，但 CoCo 已 73.52%，距满分还有空间，但未知是否存在不可逾越的语义瓶颈。
- LongText-Bench 中文 0.753 与英文 0.755 接近，说明均衡性优秀，但距离 GPT-4o 英文 0.956 仍有差距。CoCo 上限可能受限于 VAE 潜空间对中文字形的压缩损失。
- 论文未回答：代码生成和精修错误如何联合端到端优化？能否用 RL 替代完全 SFT？沙盒执行失败时的回退策略？CoCo-10K 的缩放规律？精修模型是否会过度依赖草稿导致创意丧失？

## 11. 放回研究脉络并收束

CoCo 处于三个方向的交叉点：统一多模态生成、思维链推理、结构化文生图。从 Image-Gen-CoT 到 Bagel-Think，研究者试图把推理显式化，但自然语言精度不足。CoCo 借鉴了代码执行在数学和智能体领域的成功（如 Agent RL 中代码执行），将其迁移到视觉生成。同时，CoCo 与 IRG、T2I-R1 等并行工作共同推动“中间视觉表示”在生成中的使用。作者把草稿称为“可执行 CoT”，本质是把程序合成与视觉精修结合在一个统一 MLLM 内。这种范式可能影响后续科学图表生成、海报设计、教育可视化和文档自动化。论文还提及 VideoCoCo 等延续工作（References [68]），但本文未展开讨论。

**读完必须记住的 5 件事**：

1. CoCo 用可执行 Python 代码作为思维链，代码执行得到确定性草稿图，再精修为终图；三阶段分别为代码生成、沙盒渲染、草稿引导精修（§3.2）。
2. CoCo-10K 由 Editing Dataset 和 Synthesis Dataset 组成，提供 Text-Code 对和 Text-Draft-Final 三元组，总规模约 10K（Fig. 4：通用编辑 2.5K、科学图表 2.5K、合成数据 4K、另有 1K）。
3. 训练损失只有两个：代码 token 的交叉熵和最终图像 VAE token 的 Rectified Flow MSE（Equation 1、2）；训练阶段包括 text-to-code 预微调和 16K 步全参数微调，冻结 ViT/VAE 及其 connector（§4.1）。
4. 最优训练混合比例 \(r_c=0.05\)，即 95% 精修数据 + 5% 代码数据；代码可执行性从 Bagel 的 9.1% 提升到 100%（Table 3、Fig. 7）。
5. 在 StructT2IBench 上总体准确率 73.52%，显著超过 GPT-Image 的 49.58%，但 LongText-Bench 英文仍落后 GPT-4o（0.755 vs 0.956）（Table 1、Table 2）。

**5 道自测题**：

1. CoCo 的三个推理阶段分别是什么？各阶段的输入输出是什么？
2. 为什么自然语言 CoT 不够用？代码作为 CoT 解决了哪两个精度问题？
3. CoCo 训练时冻结了哪些模块？为什么冻结它们？
4. 表 3 中 \(r_c\) 从 0.20 降到 0.05 为什么性能提升？这揭示什么训练规律？
5. 原始 Bagel 的代码编译成功率只有 9.1%，CoCo 如何解决？这一结果在图 7 中如何呈现？

最终一句话总结：CoCo 用“代码生成 → 确定草稿 → 草稿精修”的管线，把视觉生成的推理从模糊的自然语言升级为可执行、可验证的结构化中间表示，在结构化与文本密集任务上取得显著提升，但通用性、数据依赖和精修保守性仍需后续检验。
