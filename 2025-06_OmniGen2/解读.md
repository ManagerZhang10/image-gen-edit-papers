# 大白话深读《OmniGen2》

## 1. 30 秒定位

OmniGen2 是一个统一的多模态生成模型，目标不是单纯堆画质，而是让模型真正“听懂复杂指令”并在文本到图像（T2I）、图像编辑（Edit）、多图上下文生成（In-Context Generation，IC）三类任务上同时稳定工作。它把视觉语言模型（Vision Language Model，VLM）和扩散模型拆成两条通路：自回归 Transformer 负责理解指令并生成文本，扩散 Transformer 负责生成图像。VLM 用 Qwen2.5-VL-3B 初始化并基本冻结，扩散解码器约 4B 参数并随机初始化，总参数量约 3B+4B（论文 Table 2 标注）。它的核心贡献有三点：一是提出 Omni-RoPE，一种三维位置编码，区分不同图像实例并保持局部二维空间对齐；二是构建从预训练、SFT 到多任务强化学习（RL）的指令对齐流程；三是发布 OmniContext 基准，专门评估多参考图像的上下文一致性。论文的重点不是提出新扩散骨干，而是证明“渐进式多任务 RL 课程”能让基础模型在多个指标上稳定提升，并且用精心控制的消融说明哪些任务和奖励信号该选、该避开。论文还给出了数据构建管线的很多细节，说明视频源数据、高质量 inpainting 数据和反射数据如何支撑基础模型的多样能力。

## 2. 为什么这篇论文会出现

论文写的出发点很直接：多模态生成模型虽然越来越多，但它们在复杂真实场景下的指令跟随稳健性仍不够。作者观察到，许多现有开源生成模型要么太过专精，只能处理训练范围内某类任务，要么在美学偏好上被过度优化，导致模型丧失了可塑性（plasticity），也就是后续想做指令对齐时，模型已经很难被“掰回”通用方向。基础模型需要同时具备初步的指令跟随能力和充足的世界知识，又不能被过训练锁死；这是一个平衡难题。同时，多模态指令对齐需要显式且全面的奖励信号，并保证在不同生成任务之间不会互相干扰，否则容易出现某个任务涨了、另一个任务崩了的情况。

数据方面，现有编辑和上下文生成数据要么来自 inpainting 模型，覆盖任务范围有限且指令跟随差；要么从互联网检索，数据量小且图像质量低。论文明确指出 inpainting 模型在预定义指令下生成图像，往往指令与最终图像对不上，导致训练数据存在系统性误差。因此作者希望通过视频数据源构建更丰富、更一致的训练样本，并在此基础上系统性地做多任务 RL。附录 9.2 中提到，他们收集了 SEED-Data-Edit、UltraEdit、OmniEdit、PromptFix 和 ImgEdit 等公开编辑数据，但这些数据往往存在图像质量低、指令不准确和任务多样性不足的问题，于是他们自建了更受控的数据管线。

简单说，这篇论文想解决“统一模型如何从‘能生成’走向‘稳定、可控、可对齐地生成’”，而不是单点刷分。它同时面对两个挑战：一是构建一个强大但不过拟合的基础模型，二是用显式且全面的奖励信号做多任务对齐。论文将这两个挑战拆成两个阶段，分别用大规模数据构建和渐进式 RL 来回应。

## 3. 读懂前需要的最小概念

要跟上这篇论文，需要先理解几个概念。**统一多模态生成**指一个模型能够处理文本、图像输入，并输出图像或图文序列，例如同时做图像理解和生成。**视觉语言模型（VLM）**是为文本和图像联合理解设计的自回归 Transformer，能输出文本 token；它内部把图像切成 patch 并映射成 token。**扩散 Transformer / Rectified Flow**是图像生成的主流范式，它从噪声开始逐步去噪得到干净潜变量，训练目标是拟合从噪声到数据的速度场。**RoPE（Rotary Position Embedding）**是一种旋转位置嵌入，常用在 Transformer 中编码一维序列位置；OmniGen2 把它扩展成三维。**GRPO（Group Relative Policy Optimization）**是强化学习中的一种策略优化方法，通过对一组采样结果做组内相对优势估计来更新策略，不需要显式价值网络；用在扩散模型上称为 Flow-GRPO。**解耦架构**指文本生成和图像生成使用两个独立 Transformer，而不是用一个统一 Transformer 同时做两件事，这样更灵活且能保留各自预训练能力。理解这些概念后，OmniGen2 的设计就是：用 VLM 处理指令，用扩散 Transformer 生成图像，用 RoPE 变体保证多图空间一致性，再用多任务 GRPO 对齐。此外论文还涉及**奖励模型（Reward Model）**：一个用于给生成结果打分的外部模型或函数，RL 以此计算优化信号。不同任务使用不同奖励模型，例如编辑任务用 EditScore，上下文生成用 Qwen2.5-VL-72B，T2I 用 GenEval 的可验证规则奖励。

## 4. 方法全景：先看数据流

图 2 展示的是 OmniGen2 的架构。下面先给出推理时的一条核心数据流，再拆解组件。

```
用户输入：文本 prompt + 可选的多张参考图像
        │
        ├──► 文本 Tokenizer ──► 文本 token 序列 ──┐
        │                                         │
        └──► ViT Tokenizer（图像理解编码器）──► 图像 patch token ──┴─► 自回归 Transformer（VLM，Qwen2.5-VL-3B）
                                                                          │
                                                                          ├──► 生成文本回复（可选：反思、对话）
                                                                          │
                                                                          └──► 当生成 <|img|> 特殊 token 时触发图像生成
                                                                                │
                                                                                ▼
                                           提取 VLM 最后一层隐藏状态（只取文本 token 对应的隐藏状态）
                                                                                │
                                                                                ▼
       输入图像 ──► VAE 编码器（Flux-VAE）──► 低层图像特征 ────────┐
                                                                          │
       随机噪声潜变量 ──► 加噪到当前时间步 ──► 与 VLM 隐藏状态、VAE 特征一起 ──┘
                                                                                │
                                                                                ▼
                                     Refiner（两层 Transformer 对齐）→ 扩散 Transformer 主干（共享权重）
                                                                                │
                                                                                ▼
                                    多步去噪 / 流匹配后输出干净潜变量 → VAE 解码器 → 最终图像
```

**自回归 Transformer（VLM）**：输入是文本 token 和图像 token，输出是文本序列。它负责理解多模态指令、执行对话、反思以及生成触发图像生成的 `<|img|>` token。目的就是复用 Qwen2.5-VL 已学到的世界知识和语义理解。假设是：VLM 的输出隐藏状态能良好地表达高层指令语义。Qwen2.5-VL-3B 本身是一个预训练好的视觉语言模型，论文采用 Instruct 版本以保留对话和指令跟随能力。这个 VLM 提供理解与推理基础，模型在多数训练阶段保持冻结，以节省算力并避免遗忘其已有能力。

**扩散解码器**：输入是 VLM 隐藏状态、VAE 低层特征、带噪潜变量和时间步；输出预测速度场，用来去噪。它采用 Lumina-Image 2.0 的统一 Transformer 骨干，参数跨模态共享。Refiner 是一个两层 Transformer，用来对齐不同输入特征的分布。论文提到，Refiner 与 Lumina-Image 2.0 中使用的 Transformer 块架构一致，是一个轻量模块。假设是：语言和图像共享足够的语义表示，参数共享能帮助跨模态对齐，同时比分离通路更自然。低层视觉特征由 Flux-VAE 编码得到，主要提供像素级的细节约束，尤其对图像编辑中的未编辑区域保持很重要。

**Omni-RoPE**：位置编码模块，输入是 token 的空间坐标和所属图像实例编号；输出三维位置标识 `(Δ_I^(k), h, w)`。目的就是让模型既能区分不同图像，又能在同一图像内保持局部二维结构。假设是：实例身份和局部空间坐标应该解耦，否则编辑和多图任务容易发生空间错乱。论文的 toy 实验显示，这种设计比先前 Lumina-Image-2.0 和 Qwen2-VL 的 RoPE 变体收敛更快、最终 loss 更低。

**RL 对齐课程**：训练阶段按顺序组织任务：先是编辑任务，用 EditScore 作为奖励；然后是 T2I 任务，用 GenEval 的可验证奖励；最后是上下文生成任务，用 Qwen2.5-VL-72B 作为奖励模型。当前模型在训练时大部分时间冻结 VLM，只优化扩散解码器。论文还引入 reflection 数据微调，使模型具备多轮自我纠正能力，但这部分内容不是 RL 课程的核心，而是基础模型能力的一部分。

## 5. 核心公式与直觉

论文中最关键、并且明确给出的公式是 Omni-RoPE 的位置标识（Equation 1）：

\[
\text{PosID}_k(h,w) = (\Delta^{(k)}_I,\ h,\ w)
\]

变量解释：\(k\) 是第 \(k\) 个图像或模态实例；\(\Delta^{(k)}_I\) 是这个实例的“实例身份”偏移（instance identity），同一张图像内的所有 token 共享同一个 \(\Delta^{(k)}_I\)；\((h,w)\) 是该 token 在该图像内的局部二维坐标，从 \((0,0)\) 开始计算。对于文本 token，这个公式自然退化为标准一维位置索引，因为没有二维空间结构，所以文本 token 在 Omni-RoPE 中只保留一维位置信息。

这个公式的直觉核心是“身份与空间解耦”。传统的 RoPE 变体可能把多个图像的坐标全局连续拼接，例如 Lumina-Image-2.0 使用 `(0, h+Δh, w+Δw)`，Qwen2-VL 使用 `(ΔI, h+ΔI, w+ΔI)`（见 Table 1）。这样输入图像和输出图像对应的 patch 可能无法得到相同的空间嵌入，导致编辑时细节不一致。Omni-RoPE 让每个图像的 h 和 w 都从局部坐标算起，因此输入图像中某个 patch 与输出图像中同一位置的 patch 得到相同的空间分量；同时实例身份维度 \(\Delta_I\) 用于区分不同图像。想象你在编辑一张图，如果把背景里的天空、人物、前景都混在一个全局坐标里，模型很难知道“这个像素位置在输出图中应该保持原样”。Omni-RoPE 等于给每张图加了一个独立的坐标系，再用一个额外的“哪张图”标签区分来源。

论文用一个 toy reconstruction 实验验证这个设计：随机初始化模型，输入多张随机采样图像，训练模型重建第 \(k\) 张图像。Table 1 显示，Omni-RoPE 大约 800 步达到 loss<0.014，最终 loss 0.003；Lumina-Image-2.0 的 RoPE 需要约 2500 步，最终 0.017；Qwen2-VL 的 RoPE 需要约 1200 步，最终 0.005。再加入 image index embedding 后收敛步数约 800 不变，但最终 loss 降到 0.002。这个实验把位置编码的效果从完整模型中隔离出来，确认了“身份和空间解耦”确实能加快多图空间对应关系的建立，并且降低最终重建误差。附录 Figure 9 提供了完整 loss 曲线，显示 Qwen2-VL 的 RoPE 在早期有明显的平台期，Lumina 版本长期不稳定且收敛到更差解，而 Omni-RoPE 变体晚期 loss 更低更稳定。

另一个公式没有在论文正文展开，但 RL 对齐阶段用的是 Flow-GRPO。论文只是引用，未给出具体公式，所以我们不能用编造的公式去填充。从 Table 5 可以看到它的工程表现：每一步 RL 都选取某些任务、奖励信号，并按顺序训练一定步数，最终目标是最大化组内相对优势，同时不同任务之间通过课程顺序做迁移。RL 训练步数在 Table 5 下方明确标注：T2I、Edit、IC 任务分别训练 1500、700、200 步。这个步数分配体现了课程设计：先编辑 700 步，再 GenEval 1500 步，最后 IC 200 步。

## 6. 训练到底怎么跑

训练流程分两大阶段：基础模型构建，以及 RL 指令对齐。附录 Table 6 给出了明确配置。

**预训练阶段**：从零开始训练扩散解码器。分辨率课程是 256² → 512² → 1024²。每个分辨率下，先用纯文本到图像（T2I）任务训练，再引入混合任务（包括图像编辑和上下文生成）。步数在 256² 时 T2I-only 50k 步，混合任务 50k 步；512² 时各 30k 步；1024² 时各 50k 步。使用的目标函数是 Rectified Flow，即学习一条从噪声通向数据的直线路径。模型优化主要针对扩散解码器；VLM 在“训练过程的大部分时间”被冻结（论文 §3.4 写明）。数据集约 140M 开源图文对，加上 10M 私有图像，私有图由 Qwen2.5-VL-72B 生成标注。理解能力数据采用 LLaVA-OneVision。为了处理变长上下文，用 FlashAttention2 提升序列处理效率。

**SFT 阶段**：在 1024² 分辨率上，混合任务训练 100k 步。这一步的目标是进一步精修高层推理和组合能力，并使用来自私有模型的蒸馏数据。SFT 后基础模型获得了初始指令跟随能力和多样生成能力。论文还提到在预训练和 SFT 之间构建了 interleaved 和 reflection 数据集，前者从视频源得到约 0.8M 个交错图文序列样本，用来预训练模型处理连续多模态序列的能力；后者则通过多轮生成-反思-修正数据赋予模型自省能力。

**RL 对齐阶段**：在 512² 分辨率上，总共 2.4k 步。论文把这个阶段组织成三阶段课程。第一任务 \(T_1\) 是图像编辑，使用 EditScore 作为奖励模型，训练步数 700；第二任务 \(T_2\) 是 T2I，使用 GenEval 的可验证奖励，训练步数 1500；第三任务 \(T_3\) 是上下文生成，使用 Qwen2.5-VL-72B 作为奖励模型，训练步数 200。RL 数据规模：50k T2I prompts、110k 编辑样本、180k 上下文生成数据。优化器为 Flow-GRPO，在线采样一组候选，用奖励模型打分，计算组内相对优势后更新。RL 分辨率降到 512² 是出于计算效率考虑，因为 RL 需要在线生成样本，高分辨率会显著增加采样成本。

训练中一个关键决策是剔除 HPSv3 这类美学奖励，因为论文发现它容易导致奖励黑客（reward hacking）；另一个关键决策是排除 OCR 等技能重叠度低的任务，因为会带来负干扰。附录 Table 10 进一步显示，完整课程在 OOD 基准 Emu-Edit 和 OneIG-Bench 上也有提升，说明该 RL 课程并非只是过拟合训练奖励。

## 7. 推理到底怎么跑

OmniGen2 的完整推理顺序可以描述为以下步骤，与图 2 和 §3.1-3.2 一致：

1. **输入准备**：用户提供文本指令，可选包含一张或多张参考图像。文本通过文本 tokenizer 编码；参考图像通过 ViT tokenizer 编码成图像 patch token，与文本 token 拼接进入自回归 VLM。
2. **VLM 自回归生成**：VLM 逐 token 生成回复。如果用户任务只是理解，比如描述图像，就直接输出文本结束。如果用户指令涉及生成或编辑，VLM 会生成一个特殊 token `<|img|>`，这个 token 是触发图像生成的开关。这个 token 是一个可学习的特殊标记，它的出现只是文本序列中的一个信号，模型通过训练学会了在需要生成图像时输出它。
3. **提取语义条件**：当 `<|img|>` 出现时，提取 VLM 最后一层的隐藏状态。论文特别指出只使用文本 token 对应的隐藏状态，因为视觉细节已经由 VAE 特征承担了。这样避免重复编码视觉信息，减少冗余并让条件更紧凑。这些隐藏状态作为高层语义条件送入扩散解码器。
4. **提取低层视觉特征**：输入的参考图像或编辑原图通过 Flux-VAE 编码器得到低层潜变量特征，作为保持细节一致性的条件。VAE 特征提供的是结构和纹理层面的信号，与 VLM 的高层语义形成互补。
5. **扩散生成**：随机采样噪声潜变量，按 Rectified Flow 的时间步调度。噪声潜变量与 VLM 隐藏状态、VAE 特征一起送入 Refiner 对齐，再经过扩散 Transformer 主干逐步去噪。Omni-RoPE 为所有 token（包括条件图像、VLM 语义 token、噪声潜变量）提供统一位置编码，确保空间归属和实例区分在去噪的每一步都被保留。
6. **解码输出**：去噪后的干净潜变量送入 VAE 解码器，得到最终图像。如果 VLM 还生成了文本说明或反思，则图像与文本一起输出。
7. **可选反思循环**：模型经过反射数据微调后，能够在第一轮生成后继续产生文本反馈，判断是否满足用户要求，并决定是否需要再次生成或停止。这会形成多轮生成流程，直到模型判断满足或用户停止。论文在反思数据部分指出，他们先尝试用 DSG 评估框架做指令-图像对齐，但 DSG 经常产生幻觉，后来改用 Doubao-1.5-pro 作为评判器，生成问题和修改建议。经过多轮迭代，模型可以在测试时进行多次生成和修正，但其仍可能出现过度反思或错误修正。

推理时模型只需要一次 VLM 前向加多步扩散去噪。论文没有披露采样步数，但扩散 Transformer 约 4B 参数，相对于许多 20B 级模型更轻量。在实际推理中，VLM 只需生成到 `<|img|>` 之后的停止条件即可，因此文本自回归长度通常很短，主要的计算负担在扩散去噪部分。

## 8. 实验和消融到底证明了什么

实验主要集中在三类任务和统一理解能力。以下表格给出至少 4 条关键证据：

| 证据 | 指标与对照 | 证据锚点 | 支持结论 |
|---|---|---|---|
| T2I 组合生成 | OmniGen2 在 GenEval Overall 得分 0.95，超过 UniWorld-V1（0.84）、BAGEL（0.88）和专用模型 Qwen-Image（0.91） | Table 2; Table 11 | RL 对齐策略显著提升基础模型的复杂 prompt 组合生成能力 |
| 图像编辑平衡 | Emu-Edit 上 CLIP-Out 0.311 为最高，CLIP-I 0.896 和 DINO 0.876 居前；GEdit-Bench 上 Overall 7.21，高于 Gemini 2.5 Flash Image（7.10），仅次于 Qwen-Image-Edit-2509（7.54） | Table 3 | 模型能在施加编辑的同时保持未编辑区域一致性 |
| 上下文生成 | OmniContext Overall 7.95，其中 SINGLE 8.41、MULTIPLE 7.73、SCENE 7.86；超过 Qwen-Image-Edit-2509（7.69），低于 GPT-4o（8.80） | Table 4; Table 7-9 | 多图一致性能力强，但与闭源最强模型仍有差距 |
| 消融：基础模型 vs RL | Base (w/o RL) 在 GenEval 0.78、OmniContext 7.18、GEdit Overall 6.28；最终 RL 课程分别提升至 0.95、7.95、7.21 | Table 5 | 渐进式多任务 RL 对所有核心任务都有明显增益 |

最关键消融在 Table 5。它比较了不同 RL 策略。论文发现四个要点：第一，技能重叠度低的任务会互相干扰，例如“OCR only”训练让 GEdit Overall 从 6.28 降到 6.13，同时 GenEval 仍只有 0.78。第二，有技能重叠的任务有正迁移，例如“Edit & GenEval”策略分别在 GenEval 和 GEdit 上超过单任务基线，GenEval 从 0.79 或 0.94 提升到 0.95，GEdit Overall 从 7.01 或 6.30 提升到 7.19。第三，人类偏好奖励风险很高，例如“Edit & HPSv3”把感知质量 PQ 刷到 8.22，但语义一致性 SC 崩塌至 6.87，同时 OmniContext 掉到 6.82，这是典型的奖励黑客。第四，准确性奖励信号至关重要，“Edit only”在 IC 上的得分（7.71）甚至高于“IC only”（7.38），因为编辑奖励模型 EditScore 有助于学习通用指令跟随。另外，训练顺序也重要：最终顺序 Edit→GenEval→IC 得到 GEdit Overall 7.21，而改为 Edit→IC→GenEval 则只有 7.06；作者假设编辑任务提供了更丰富的监督，打好基础再学后续任务更好。

OOD 附录 Table 10 进一步支持这一结论：完整课程 Edit→GenEval→IC 在 Emu-Edit 的 CLIP-I/DINO 上达到 0.896/0.876，在 OneIG-Bench Align. 上达到 0.8289，均高于 Base（0.877/0.823/0.7870）和另一种顺序 Edit→IC→GenEval（0.868/0.826/0.8242）。这说明 RL 课程没有只过拟合训练奖励，而是习得了可迁移的能力。

尚未证明的主张：Omni-RoPE 的优势只在 toy 重建实验中验证，论文没有给出在真实多任务训练中移除 Omni-RoPE 的消融；反射能力只在有限 T2I 数据上训练，且论文自己指出 3B VLM 感知能力有限、会过度反思；OmniContext 虽是新基准，但只评估了少数模型，且其评分依赖 GPT-4.1 的主观判断，长期稳定性和与其他指标的相关性尚未充分论证。另外，论文未披露 RL 在线采样时的具体组大小、KL 系数等超参数。

## 9. 与前作怎么选

最接近的方案有四个：OmniGen 前作、BAGEL、MetaQuery、Qwen-Image-Edit。

**OmniGen**（前作）：统一图像生成模型，3.8B 参数。在 OmniContext 上 Overall 仅 4.34，GenEval 0.68，编辑也较弱。OmniGen2 通过引入 VLM 隐藏状态、Omni-RoPE 和 RL 对齐，性能大幅提升。如果只需要轻量、简单生成且不追求高一致性，OmniGen 可能仍然可考虑，但论文没有给出选择场景。

**BAGEL**：7B+7B 的双 Transformer 统一模型，理解指标强（MMBench 85.0），但生成编辑一致性较弱，OmniContext 5.73。OmniGen2 参数更小（3B+4B），却达到 GenEval 0.95 和 OmniContext 7.95。如果需求偏向多模态理解而非精细编辑生成，BAGEL 可能仍有优势，因为其 MMBench 85.0 明显高于 OmniGen2 的 79.1；但如果目标是生成和编辑，OmniGen2 在更小参数下表现更好。

**MetaQuery**：使用固定长度的可学习查询 token 压缩指令信息，存在信息瓶颈。OmniGen2 直接用变长 VLM 隐藏状态避免这个瓶颈。如果输入指令很长或包含多图复杂语义，OmniGen2 更合适；如果偏好在特定硬件上高度固定的条件编码，MetaQuery 的设计更规整。论文明确说两者概念相似，只是执行不同：MetaQuery 用固定长度 query tokens，OmniGen2 用变长隐藏状态，后者避免了信息瓶颈。

**Qwen-Image-Edit-2509**：在 GEdit-Bench 上 Overall 7.54 略高于 OmniGen2 的 7.21，但参数量为 7B+20B，且在 OmniContext 上下文一致性上 7.69 低于 OmniGen2 的 7.95。如果部署预算有限，又要做多参考图上下文生成，OmniGen2 是更具性价比的选择；如果主要做单一图像编辑且可以部署大模型，Qwen-Image-Edit 可能更好。

总体而言，无硬性绝对最优。OmniGen2 适合需要统一生成、编辑、上下文一致性，并且希望在较小参数量下获得较好指令跟随的场景；不适合作为超大模型纯画质赛道的替代品。在选择时需结合实际部署约束和任务侧重，不能只看单一总分。

## 10. 工程判断：可行性、风险与上限

从论文披露的信息看，OmniGen2 的工程可行性较高，但复现和闭环部署仍有不少风险。

**数据**：训练数据规模巨大，预训练用约 140M 开源图文对加 10M 私有图。私有图和不公开的数据管线是复现壁垒。视频数据构建管线依赖 SAM2、Grounding DINO、FLUX.1-Fill 和多个 VLM，每一步都会引入工具模型的误差。论文附录明确指出 inpainting 模型指令跟随差，所以选择随机填充再写指令，但这也会限制编辑指令的精确性。想要复现完整数据几乎不可能，只能参考论文提出的思路。此外，数据管线中多个步骤都依赖 Qwen2.5-VL 系列模型做过滤和描述，这意味着数据质量受这些模型能力上限影响，存在系统偏差。

**算力/延迟**：扩散部分约 4B 参数，VLM 3B，属于中等规模。但 Rectified Flow 多步采样加上在线 RL 训练，训练成本很高。推理延迟主要由扩散步数决定，论文未披露具体值，但每张图至少需要多次前向传播。若部署在移动端，4B 扩散 Transformer 仍偏重。RL 阶段使用 512² 分辨率，说明在线采样在 1024² 下成本不可忽视。

**实现难点**：Omni-RoPE 需要精确处理三段位置（实例 ID、h、w），避免与 attention mask 冲突；VLM 冻结与扩散解码器之间的梯度边界需要小心控制；Flow-GRPO 在线采样需要稳定的奖励模型服务，否则训练不稳定；Refiner 虽然轻量，但如何在语义条件、低层特征、噪声之间正确对齐需要调参。此外，反射机制涉及多轮生成和早期停止，推理时会增加控制逻辑和延迟。

**失败环节**：论文自己指出几个明显弱点——中文 prompt 效果差于英文、人体形状修改困难、对低分辨率或低质量输入图像高度敏感、多图输入存在歧义、上下文生成偶尔无法精确复制对象。这些在 Figure 8 都有对应示例。论文还提到在 in-context generation 中偶尔无法完美复制上下文对象，提高 guidance scale 也只能部分缓解，猜测需要进一步扩大模型规模才能根本改善。

**监控信号**：训练时应重点关注 Table 5 中暴露的奖励黑客现象。例如 HPSv3 组 PQ 虚高但 SC 和 IC 崩塌。实际工程中需要同时监控编辑一致性（CLIP-I/DINO）、指令跟随（CLIP-Out/SC）、上下文一致性（PF/SC），并设置 KL 散度或奖励方差控制。论文未披露 RL 过程中的 KL 正则细节，只提到使用 Flow-GRPO。

**指标上限与未回答问题**：GenEval 已经 0.95，主要瓶颈是 color attribution（0.86）和 counting（0.93），说明模型对复杂数量与属性绑定的组合语义仍有不足。OmniContext 与 GPT-4o 的 8.80 相比还有明显差距。论文未回答模型规模提升是否真能解决上下文生成中的偶尔失利；也未回答 Omni-RoPE 在真实训练任务中单独贡献有多大；反射能力的在线 RL 增强被明确留作未来工作。所以如果要继续扩展，应该优先解决模型规模、中文/低质输入鲁棒性和上下文复制精度，而不是继续堆美学奖励。

## 11. 放回研究脉络并收束

OmniGen2 处于统一多模态生成与 RL 对齐的交汇点。它继承了 OmniGen、UniReal、BAGEL 等把理解和生成放进一个框架的思路，但用解耦架构降低训练成本；它借鉴 MetaQuery 的条件机制但替换成变长隐藏状态；它引入 Flow-GRPO 的多任务课程，把扩散模型 RL 从单任务推向多任务协同。相比纯粹追求画质的 Flux、Qwen-Image，它的卖点是“统一模型在被 RL 对齐后不牺牲任何任务”。但论文也坦承离通用多模态系统还有距离，尤其是规模、多语言和鲁棒性。

**读完必须记住的 5 件事**：

1. OmniGen2 采用解耦架构：冻结的 Qwen2.5-VL-3B 提供语义条件，约 4B 的扩散 Transformer 负责图像生成，两者通过隐藏状态连接。
2. Omni-RoPE 用 `(Δ_I, h, w)` 把实例身份和局部二维坐标解耦，使多图编辑和上下文生成的空间一致性更好；toy 实验表明它收敛更快、最终 loss 更低。
3. 基础模型训练分预训练分辨率课程和 SFT，核心是避免过训练、保持可塑性；预训练从 256² 到 1024²，每个分辨率先 T2I 后混合任务。
4. RL 对齐是三阶段课程 Edit→GenEval→IC，用不同奖励信号，删掉 HPSv3 防止奖励黑客；消融显示任务选择和顺序对最终性能影响显著。
5. OmniContext 是论文提出的多图上下文生成基准，OmniGen2 Overall 7.95，超过多个开源模型但与 GPT-4o 有差距，且该基准依赖 GPT-4.1 做评分。

**5 道自测题**：

1. OmniGen2 为什么不使用 MetaQuery 的固定长度 query token，而改用 VLM 的变长隐藏状态？
2. 在 Omni-RoPE 中，同一张图像内的不同 patch 共享什么、不共享什么？为什么这样设计能帮助图像编辑？
3. 在 RL 消融中，加入 HPSv3 美学奖励后发生了什么现象？这说明什么风险？
4. 预训练阶段的分辨率课程按什么顺序进行？每个分辨率下为什么先 T2I 再混合任务？
5. OmniContext 的三个任务类型 SINGLE、MULTIPLE、SCENE 分别评估什么能力？论文用哪个指标作为总体分？

最终一句话总结：OmniGen2 用“解耦架构 + Omni-RoPE + 渐进式多任务 RL”证明，一个中等规模的统一生成模型可以通过谨慎的任务与奖励调度，在不牺牲编辑和上下文一致性的前提下，把指令跟随能力系统性地推高。
