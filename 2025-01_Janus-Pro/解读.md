# 大白话深读《Janus-Pro》

## 1. 30 秒定位

Janus-Pro 是 DeepSeek-AI 于 2025 年 1 月 29 日发布在 arXiv 的统一多模态模型，论文编号 2501.17811。它用一个自回归 Transformer 同时完成图像理解和文生图，并沿用 Janus 的核心设计：视觉编码解耦。理解任务使用 SigLIP 编码图像，生成任务使用 VQ tokenizer 把图像变成离散 ID，两条路径互不干扰，再由同一个 LLM 处理。论文标题中的“Data and Model Scaling”指向三条改进：优化训练策略、扩充训练数据、把模型从 Janus 的 1.5B 扩展到 Janus-Pro 的 1B 与 7B 两档（其中 Janus-Pro-1B 底层 LLM 为 1.5B，Janus-Pro-7B 为 7B，见 Table 1/Table 3）。在理解侧，Janus-Pro-7B 的 MMBench 达到 79.2，超过前作 Janus 的 69.4、TokenFlow-XL 的 68.9 和 MetaMorph 的 75.2（§3.3, Table 3）；POPE 87.4、MME-P 1567.1、SEED 72.1、GQA 62.0、MMMU 41.0、MM-Vet 50.0。生成侧，GenEval 整体 0.80，超过 Janus 的 0.61、DALL-E 3 的 0.67、SD3-Medium 的 0.74（Table 4）；DPG-Bench 整体 84.19，略高于 SD3-Medium 的 84.08（Table 5）。但 Janus-Pro 的输入和输出都被限制在 384×384 分辨率，论文在 §4 明确承认这会影响 OCR 和细粒度生成。这篇笔记的目标是让你能画出训练和推理的数据流，说清为什么 Stage II 要丢弃 ImageNet、合成美学数据为什么重要，以及哪些结论有强证据、哪些只是观察。

## 2. 为什么这篇论文会出现

统一多模态模型的动机很直接：用一个 Transformer 同时做图像理解和图像生成，可以减少模型冗余，并提高文生图的指令遵循能力。早前很多方法为了统一，让理解和生成共用同一个视觉编码器（§1）。但理解和生成所需的表示并不相同：理解需要高层语义信息，比如物体类别、场景关系；生成需要可解码的局部细节和空间结构，比如纹理、边缘、颜色布局。共用编码器往往导致理解性能次优，因为编码器要在两种目标之间折中。Janus 提出“解耦视觉编码”：给理解和生成各配一个独立编码器，中间用统一的自回归 Transformer 处理。这个设计在 1B 规模被验证有效，但 Janus 仍然存在两个明显缺点：一是短 prompt 文生图效果不佳，二是生成质量不稳定。论文把原因归结为训练数据有限和模型容量小（§1）。Figure 2 的定性对比展示了 Janus 在短 prompt 下输出不稳定、细节缺失，而 Janus-Pro-7B 能生成黑板上写“Hello”这类简单文字。

因此，Janus-Pro 的目标不是提出新架构，而是对 Janus 做一次系统的工程放大。论文在三处动手。第一，修正训练策略：原 Janus 在 Stage II 把 66.67% 的文生图训练步用于 ImageNet 类别名生成，目标是先建模像素依赖，但作者通过后续实验发现这种做法“次优且计算效率低”（§2.2）。第二，扩展数据：理解侧参照 DeepSeek-VL2 增加约 90M 样本，包括图像 caption、表格/图表/文档理解等；生成侧加入约 72M 合成美学数据，使统一预训练阶段真实与合成数据的比例达到 1:1（§2.3）。第三，模型容量从 1.5B LLM 放大到 7B，并观察损失收敛是否加快、下游指标是否进一步提升（§2.4）。整体动机是证明解耦视觉编码不是一个小模型的特殊技巧，而是一个可随数据和模型规模扩展的通用方案。Figure 1 用基准散点图展示平均性能提升，其中理解平均得分在 Janus-Pro-7B 上达到约 64，在 Janus-Pro-1B 上约 58，高于 Janus 与同规模 LLaVA 系列；生成侧 GenEval 与 DPG-Bench 的柱状图显示 Janus-Pro-7B 两项均高于前作和多个专用模型。这些图例说明规模扩展带来了整体收益，但具体到各任务仍需看表格分项。

## 3. 读懂前需要的最小概念

要理解 Janus-Pro，需要先掌握四个关键概念：多模态理解、文生图、自回归建模和视觉编码解耦。**多模态理解**指输入图像和文本指令，输出文本回答，常见任务包括描述、问答、OCR、地标识别等。**文生图**指输入文本 prompt，输出图像。Janus-Pro 不是直接预测像素，而是以自回归方式逐步生成离散视觉 token，最后用 VQ 解码器重建图像。

**自回归 Transformer** 是语言建模的标准框架：按条件概率链 \(p(x_t\mid x_{<t})\) 逐步预测下一个 token。Janus-Pro 把文本 token 和图像 token 放进同一个序列，由同一个 LLM 处理（§2.1）。**视觉编码解耦**是本文的核心思想。理解需要高层语义，所以理解编码器使用 SigLIP-Large-Patch16-384，输出连续高维语义特征；生成需要局部细节和可解码结构，所以生成编码器使用 VQ tokenizer，codebook 大小为 16,384，下采样 16 倍，把 384×384 图像变成 24×24=576 个离散 ID（§3.1）。两者独立，互不干扰。

**Adapter** 是两层 MLP，用来把不同编码器的输出映射到 LLM 输入隐空间。论文中有两个 adapter：理解适配器和生成适配器（§2.1/§3.1）。**VQ tokenizer** 把图像编码为离散 ID，每个 ID 对应 codebook 里的一个嵌入向量；解码器能从 ID 序列重建图像。它引入的重建损失会在生成结果中留下细节损失，这是论文 §4 承认的生成瓶颈之一。**图像预测头** 是一个随机初始化的输出头，专门用于预测图像 ID 序列；文本输出使用 LLM 内置的预测头。两者共享 Transformer 隐藏状态，但参数独立。**序列打包** 是训练效率技巧：把多个训练样本拼接成一个长序列，减少 padding 浪费，提高 GPU 利用率（§3.1）。理解这些概念后，数据流和训练阶段就不会陌生。

需要特别注意：生成编码器的 VQ 过程是一个离散瓶颈，训练时图像通过 VQ 编码器得到 ID 序列，再通过生成适配器映射为嵌入；推理时模型预测 ID，交给 VQ 解码器。整个过程没有扩散模型的迭代去噪，而是像语言模型一样逐 token 采样。这也是 Janus-Pro 生成速度快于部分扩散模型的潜在原因，但论文没有给出推理时间数据。

## 4. 方法全景：先看数据流

Janus-Pro 的架构与 Janus 完全相同（§2.1）。理解路径和生成路径共享同一个自回归 Transformer，但输入编码器不同。下面是训练与推理的核心数据流：

```
[理解训练/推理]
图像 384×384
  → SigLIP-Large-Patch16-384 编码器 → 2D 特征网格展平为 1D 序列
  → Understanding Adapter（两层 MLP）→ LLM 输入空间向量
文本指令 → Text Tokenizer → 文本 token 嵌入
拼接 [图像特征..., 文本 token...]
  → 自回归 Transformer → 文本预测头 → 文本 token 序列
  → Text De-Tokenizer → 回答

[生成训练/推理]
文本 prompt → Text Tokenizer → 文本 token 嵌入
  → 自回归 Transformer → 图像预测头 → 图像 ID 序列（逐步采样）
  → VQ tokenizer Decoder → 384×384 图像

[训练时若提供真实生成目标图像]
真实图像 → Generation Encoder（VQ tokenizer）→ 离散 ID 序列
  → Generation Adapter 映射 codebook 嵌入
  → 与文本 prompt 拼接 → Transformer 预测下一个图像/文本 token
```

训练时，理解样本的输入是“图像+问题”，目标是文本答案；生成样本的输入是“文本 prompt”，目标是目标图像的 VQ ID 序列。数据混合比例写在 Table 2：Stage I 为 1:0:3，Stage II 为 2:3:5，Stage III 为 5:1:4，分别对应多模态理解、纯文本、视觉生成三类数据。Figure 3 的架构图也标出了“Und. Encoder”和“Gen. Encoder”两条独立路径。

下面逐个拆解核心组件：

- **理解编码器 SigLIP-Large-Patch16-384**：输入 384×384 图像，输出高层语义特征序列。目的是保留全局语义和文本可对齐的信息，不负责像素重建。它在 Stage I、Stage II 冻结，Stage III 解锁参数（§2.2）。假设是高层语义特征足以支撑下游理解任务，而冻结前期可以防止大规模噪声数据破坏预训练表示。SigLIP 本身是 CLIP 的变体，在图像-文本对比预训练中天然对语义敏感，其输出特征通常被用作多模态 LLM 的视觉嵌入。

- **生成编码器 VQ tokenizer**：输入 384×384 图像，输出离散 ID 序列，下采样 16 倍后得到 24×24=576 个 ID（基于 §3.1 计算，论文未直接写 576）。codebook 大小为 16,384。目的是把连续图像转成自回归可预测的离散 token，让图像生成变成类似语言模型的下一个 token 预测。论文没有说明它在训练中是否更新，从“Stage II 除理解编码器和生成编码器外的所有组件更新”这句推断，生成编码器应该保持冻结，但这属于工程推断。VQ tokenizer 来自引用 [38]，该工作使用 Llama 进行可扩展的图像生成，具体训练细节见原文。

- **Understanding Adapter 与 Generation Adapter**：两者都是两层 MLP。理解 adapter 输入 SigLIP 特征，生成 adapter 输入 VQ codebook 嵌入，输出都是 LLM 隐维度向量。目的是把不同模态、不同表示空间的特征对齐到同一个输入空间，让 LLM 能统一处理。Stage I 只训练这些 adapter 和图像预测头，LLM 和其他编码器都固定。两个 adapter 的参数相互独立，这样理解特征不会污染生成特征，反之亦然。

- **自回归 Transformer**：主体是 DeepSeek-LLM 1.5B/7B，最大序列长度 4096（§3.1）。接收多模态拼接序列，输出下一个 token 的分布。其内部结构和语言模型一致，只是输入 token 可能来自图像嵌入或图像 ID 嵌入。它被假设为足够通用，能同时掌握文本和图像 token 的序列规律。Table 1 列出了两个规模的具体超参数：1B 模型嵌入维度 2048、注意力头 16、层数 24；7B 模型嵌入维度 4096、注意力头 32、层数 30，词表大小均为 100K，上下文窗口均为 4096。注意这里的“Janus-Pro-1B”实际底层 LLM 参数为 1.5B，命名可能源自总参数量取整或产品定位。

- **文本 tokenizer/de-tokenizer 与图像解码器**：文本侧是标准 tokenizer，词表大小 100K；图像侧用 VQ tokenizer 的解码器把预测 ID 序列还原成图像。论文没有给出推理采样参数，仅说明整个模型遵循自回归框架（§2.1）。文本 de-tokenizer 与 tokenizer 配对，图像解码器则与生成编码器共享同一套 VQ 码本。

整个方法的关键假设是：理解和生成需要不同表示，解耦可以避免冲突；离散 VQ ID 足以承载图像内容；一个 Transformer 通过不同输入投影和不同输出头可以同时掌握两种模态。这个假设在 Janus 1B 上成立，Janus-Pro 进一步在 7B 规模上验证。训练时的数据流是双向的：理解样本从视觉编码进入 LLM 输出文本，生成样本从文本进入 LLM 再经图像预测头输出 ID，两个方向在同一 batch 内共存。

## 5. 核心公式与直觉

论文没有给出带编号的数学公式，但方法本质是标准的自回归下一个 token 预测。我们可以把统一序列建模写成：

\[
p_\theta(x_1,\dots,x_T)=\prod_{t=1}^{T} p_\theta(x_t\mid x_{<t})
\]

其中 \(x_t\) 可以是文本 token，也可以是图像 token ID；\(T\) 是拼接序列的总长度。对于理解任务，输入 \(x\) 是图像特征与文本指令拼接后的序列，目标 \(y\) 是回答文本 token；对于生成任务，输入 \(x\) 是文本 prompt，目标 \(y\) 是目标图像的 VQ ID 序列。训练目标是最小化交叉熵损失：

\[
\mathcal{L}=-\mathbb{E}_{(x,y)\sim\mathcal{D}}\left[\sum_{t:\ y_t\neq \texttt{pad}} \log p_\theta(y_t\mid x,\ y_{<t})\right]
\]

这里 \(x\) 是输入上下文，\(y\) 是目标序列。对于理解任务，\(y\) 是回答文本 token；对于生成任务，\(y\) 是目标图像的 VQ ID 序列。这是基于论文架构的标准推断，论文本身没有写这个损失公式。文本位置的预测由 LLM 内置头给出，图像位置的预测由随机初始化的图像预测头给出，二者共享 Transformer 的隐藏状态。

直觉上，理解编码器把图像压缩成语义特征，生成编码器把图像转成离散 ID。损失对两类任务分别反向传播：理解损失更新文本头、理解适配器和 Stage III 之后的 SigLIP；生成损失更新图像头、生成适配器和 LLM。但离散 VQ 编码器本身没有梯度路径，因为 ID 是离散选择，生成编码器只能通过 adapter 的嵌入与 LLM 交互。这种“一个模型、两套输入投影、两个输出头”的结构，使同一个 Transformer 能同时做视觉问答和文生图，并且在编码层面互不污染。

图像生成时，自回归过程是：给定文本 prompt，模型按顺序预测 576 个图像 ID。每一步用 Transformer 的隐藏状态经过图像预测头得到 codebook 大小的 logits，然后从该分布中采样一个 ID。所有 576 步完成后，VQ 解码器把 ID 序列映射回 384×384 图像。文本生成同理，只是预测头不同。这个公式没有引入扩散噪声或额外损失项，整个系统就是一个条件语言模型，只不过 token 表扩展到了图像 codebook。论文没有提供温度、top-k/top-p 等采样策略，只能知道它是自回归采样。

训练时使用 teacher forcing：在预测第 \(t\) 个目标 token 时，前文输入使用真实目标 token（或图像 ID）而非模型自身采样结果。这能稳定训练，但导致推理时可能出现曝光偏差。序列打包会在同一 batch 中拼接多个样本，因此 attention mask 必须阻止跨样本信息流动，否则交叉熵的计算会出错。这些属于标准工程细节，论文只提到“使用序列打包提高训练效率”（§3.1），没有展开 mask 逻辑。

## 6. 训练到底怎么跑

Janus-Pro 的训练分三个阶段，Table 2 给出了完整超参数。1B 和 7B 的学习率、优化器、warm-up、batch size 等完全一致，只有 Stage III 训练步数不同：1B 是 80K，7B 是 40K。两个模型都使用 AdamW（β1=0.9, β2=0.95），weight decay=0，gradient clip=1.0，constant LR，warm-up steps 分别为 Stage I 600、Stage II 5000、Stage III 0。

**Stage I（适配器与图像头预热）**：20K 步，学习率 1e-3，batch 256，数据比例 1:0:3（即多模态理解:纯文本:视觉生成 = 1:0:3，没有纯文本）。更新对象只包括理解适配器、生成适配器和图像预测头，LLM 固定，两个视觉编码器也固定。论文特别强调，在 Stage I 增加 ImageNet 训练步数，只用类别名作为文生图 prompt，就能在 LLM 参数固定时建模像素依赖并生成合理图像（§2.2）。这一步解决了原 Janus 把 ImageNet 类别名生成放在 Stage II、浪费 66.67% 文生图训练步的问题。Stage I 的重点是让 adapter 和图像头先学会基本对齐，为后续大规模统一预训练做准备。ImageNet 数据只包含类别名，没有密集描述，因此适合学习像素依赖关系而不是语义遵循。

**Stage II（统一预训练）**：计划 360K 步，但实际使用 early stopping，在 270K 步停止（§3.1）。学习率 1e-4，batch 512，数据比例 2:3:5。更新对象是除理解编码器和生成编码器外的所有组件，也就是 LLM、两个 adapter 和图像预测头（§2.2）。本文的关键改动是：Stage II 完全丢弃 ImageNet 数据，直接使用正常的文生图数据，让模型根据密集描述生成图像（§2.2）。这样可以让 Stage II 的生成训练步都花在有语义、有描述的真实或合成文本-图像对上，而不是类别名这种弱 prompt，从而提升训练效率和最终生成质量。理解数据参照 DeepSeek-VL2，增加约 90M 样本，包括图像 caption（如 YFCC）、表格/图表/文档理解（如 Docmatix）等（§2.3）。生成数据加入约 72M 合成美学数据，使统一预训练阶段真实:合成比例约 1:1（§2.3）。合成数据的 prompt 公开可用，例如引用 [43] 的 Midjourney prompts。所有数据类型在同一个 step 按 Table 2 的比例混合，并使用序列打包提高效率（§3.1）。图像预处理：理解数据把长边缩放到 384，短边用背景色 RGB(127,127,127) 补齐到 384；生成数据把短边缩放到 384，长边裁剪到 384（§3.1）。注意 batch size 512 是全局批量，具体每个数据类型的微批由比例分配。

**Stage III（监督微调）**：1B 共 80K 步，7B 共 40K 步，学习率 4e-5，batch 128，数据比例 5:1:4。与 Stage II 不同，这里理解编码器 SigLIP 的参数被解锁，参与训练（§2.2）。数据比例从 Janus 的 7:3:10 调整为 5:1:4：多模态理解数据占比从 35% 提升到 50%，纯文本从 15% 降到 10%，视觉生成从 50% 降到 40%。论文解释：轻微降低文生图比例，可以在保持强生成能力的同时提升多模态理解性能（§2.2）。Stage III 的目标是通过指令微调提升对话体验和任务泛化能力，加入 MEME 理解、中文对话等数据集（§2.3）。Stage III 学习率最低，batch size 最小，说明更接近精调阶段。生成编码器在 Stage III 依然保持冻结，只有理解编码器解锁，这保证生成侧的 VQ 表示不被破坏。

训练硬件：1B 模型约 9 天 / 16 节点，7B 模型约 14 天 / 32 节点，每节点 8 张 NVIDIA A100 40GB GPU（§3.1）。训练框架是 HAI-LLM，基于 PyTorch。论文没有披露吞吐量或 MFU，也没有报告损失曲线，只说 7B 比 1.5B 的损失收敛速度显著加快（§2.4）。值得注意的是 Stage II early stopping 在 270K 步停下，说明继续训练可能没有显著收益或出现过拟合风险。

## 7. 推理到底怎么跑

推理分为理解推理和生成推理两条路径，分别对应两个视觉编码器。

**理解推理**：

1. 输入图像按理解管线预处理：长边缩放到 384，短边用背景色 RGB(127,127,127) 填充到 384×384（§3.1）。
2. SigLIP-Large-Patch16-384 编码图像，得到 2D 特征网格；展平为 1D 序列。
3. 理解适配器（两层 MLP）把图像特征映射为 LLM 输入空间向量。
4. 文本指令通过 text tokenizer 得到 token 嵌入，与图像嵌入拼接成多模态序列。拼接顺序通常是图像在前、文本在后，因为图像提供了上下文信息。
5. 自回归 Transformer 逐步生成回答的文本 token。每一步的隐藏状态经过 LLM 内置文本预测头得到下一个 token 分布，从中采样或取 argmax。
6. 直到生成结束标记，Text De-Tokenizer 把 token 序列转为自然语言回答。

**生成推理**：

1. 输入文本 prompt，text tokenizer 转换成 token 嵌入。
2. 自回归 Transformer 逐步生成图像 ID。每一步用隐藏状态经过图像预测头得到 codebook 大小（16,384）的分布，从中采样一个离散 ID。论文未披露温度、top-k/top-p 等采样策略。
3. 生成完整 ID 序列后，交给 VQ tokenizer 解码器重建图像。
4. 输出分辨率固定 384×384。下采样 16 倍意味着序列长度为 24×24=576 个 ID（基于 §3.1 计算，论文未直接写 576）。
5. 如果输入是“图像+指令”的多模态生成任务，理解编码器路径也可以参与；但论文的示例和基准以文本到图像为主（Figure 3、Table 4/5）。Figure 4 的下半部分全部是纯文本 prompt 生成。

需要强调：论文没有报告推理延迟、吞吐量或显存占用。工程上，7B 模型自回归生成 576 个图像 ID，每步都要完整执行一次 30 层 Transformer 的前向传播；如果不使用 KV cache 或投机解码，生成一张图的算力成本不低。推理阶段是否使用 KV cache、混合精度、批处理策略等均未披露。这些都只能基于标准自回归工程实践推断，而不是论文写明的结论。理解推理只需要生成一段文本，代价远低于图像生成。

## 8. 实验和消融到底证明了什么

论文在多个基准上评估 Janus-Pro。理解评估用 POPE、MME-Perception、MMB、SEED、GQA、MMMU、MM-Vet（§3.2）；生成评估用 GenEval 和 DPG-Bench（§3.2）。以下关键证据表汇总了主要结果：

| 证据 | 任务/数据集 | 关键结果 | 对照 | 锚点 |
|---|---|---|---|---|
| 1 | 多模态理解 MMBench | Janus-Pro-7B 79.2 | Janus 69.4；TokenFlow-XL 68.9；MetaMorph 75.2 | §3.3, Table 3 |
| 2 | 多模态理解多指标 | Janus-Pro-1B MMB 75.5、MMMU 36.3、MM-Vet 39.8 | Janus(1.5B) 69.4/30.5/34.3 | Table 3 |
| 3 | GenEval 总体 | Janus-Pro-7B 0.80 | Janus 0.61；DALL-E 3 0.67；SD3-Medium 0.74；Transfusion 0.63 | §3.3, Table 4 |
| 4 | DPG-Bench 总体 | Janus-Pro-7B 84.19 | Janus 79.68；DALL-E 3 83.50；SD3-Medium 84.08；Emu3-Gen 80.60 | §3.3, Table 5 |
| 5 | GenEval 分项 | Janus-Pro-7B 计数 0.59、位置 0.79、颜色属性 0.66 | Janus 计数 0.30、位置 0.46、颜色属性 0.42 | Table 4 |
| 6 | DPG-Bench 分项 | Janus-Pro-7B Global 86.90、Entity 88.90、Attribute 89.40、Relation 89.32 | Janus 82.33/87.38/87.70/85.46 | Table 5 |
| 7 | 定性短 prompt/文字生成 | Janus-Pro-7B 更稳定，能生成黑板上“Hello” | Janus 输出不稳定或细节差 | Figure 2 |

Table 3 中理解任务的整体趋势是 Janus-Pro-7B 几乎在所有指标上领先于同规模统一模型和理解专用模型。例如 SEED 72.1，高于 Emu3-Chat 的 68.2、TokenFlow-XL 的 68.7，也高于 LLaVA-v1.5-7B 的 58.6 和 ILLUME 的 72.9 之一；MMMU 41.0 显著高于 Janus 的 30.5、TokenFlow-XL 的 38.7、ILLUME 的 38.2，但低于部分未列出的更大模型。Janus-Pro-1B 的 POPE 86.2 虽比 Janus 87.0 略低，但 MMB 从 69.4 升到 75.5，MMMU 从 30.5 升到 36.3，MM-Vet 从 34.3 升到 39.8，说明 1B 版本在推理类任务上增益明显。需注意 MME-P 分数在 Figure 1 中被除以 20 缩放到 [0,100]，Table 3 中为原始分，Janus-Pro-7B 的 1567.1 除以 20 约为 78.36，这在理解平均中会被拉高。

表 4 的 GenEval 分项尤其值得注意：Janus-Pro-7B 在 Single Object 上 0.99、Two Objects 0.89、Counting 0.59、Colors 0.90、Position 0.79、Color Attribution 0.66。虽然计数从 Janus 的 0.30 提升到 0.59，但仍然是六项中最低的，说明复杂计数能力依然是明显短板。与 SD3-Medium 相比，Janus-Pro-7B 在 Position 项 0.79 对 0.33、Color Attribution 0.66 对 0.60 有优势，但 Counting 0.59 对 0.72 落后，说明自回归离散 token 在精确数量建模上不如扩散模型的连续空间。DPG-Bench 分项中，Janus-Pro-7B 的 Attribute 和 Relation 都达到 89 以上，只有 Global 86.90 相对较低，这可能与全局构图或长距离一致性有关。

最关键消融/观察：本文没有传统的独立消融表。最接近的消融证据是训练策略调整：原 Janus Stage II 把 66.67% 文生图训练步用于 ImageNet 类别名，Janus-Pro 改为 Stage I 充分训练 ImageNet、Stage II 完全移除 ImageNet。§2.2 明确写“我们发现这个策略次优且导致显著的计算效率低下”。最终生成指标从 Janus 到 Janus-Pro 的提升（GenEval 0.61→0.80，DPG 79.68→84.19）支持这一改动有效，但它和其他改动混在一起，无法单独归因。数据比例从 7:3:10 改为 5:1:4，降低了文生图比例，但 MMBench 从 69.4 升到 79.2，MMMU 从 30.5 升到 41.0，同时 GenEval 从 0.61 升到 0.80，这说明“降低生成比例后仍能保持生成并提升理解”的命题被 Table 3/4 共同支持。合成美学数据：加入约 72M 后，论文称模型在合成数据上收敛更快，输出更稳定、美学质量更好（§2.3）；这是文字观察，论文没有给出训练曲线或消融曲线。模型规模：从 1.5B 到 7B，论文称两种损失的收敛速度显著加快（§2.4），但同样没有提供损失曲线图；从 Table 3/4/5 看，7B 大体优于 1B，但个别指标如 DPG 的 Global 分项 7B 比 1B 低 0.68，说明规模增益不是完全单调。Figure 1 的平均理解得分也显示 Janus-Pro-1B 约为 58、7B 约为 64，相比同规模 LLaVA-v1.5-Phi-1.5 和 LLaVA-v1.5-7B 均有提升，但该图没有误差棒。

尚未证明的主张：论文没有量化单一改进的净贡献，例如单独加合成美学数据、单独改训练策略、单独放大模型分别带来多少提升；没有证明解耦视觉编码在 7B 规模比共享编码有因果优势，因为所有对比都在不同模型之间而非仅交换编码策略；没有给出推理成本或质量-效率权衡；没有证明 384 分辨率足以覆盖精细 OCR 任务，结论 §4 甚至承认限制。此外，Figure 2 的定性展示只有示例，没有人类偏好评分。Janus-Pro 在 DPG-Bench 上超过 SD3-Medium 但仅高 0.11，这个差距是否统计显著，论文没有报告置信区间。

## 9. 与前作怎么选

与 Janus-Pro 最接近的方案是前作 Janus，以及统一模型 Show-o、TokenFlow-XL、Emu3，还有专用生成模型 SD3-Medium、DALL-E 3。在做选择时，需要根据任务目标和约束判断。

**选 Janus-Pro 的情况**：需要同时做多模态理解和文生图，并且希望只维护一个模型权重。Janus-Pro-7B 的 GenEval 0.80、DPG 84.19 达到或超过部分专用生成模型（Table 4/5），MMBench 79.2 也高于 TokenFlow-XL 68.9、MetaMorph 75.2（Table 3）。算力或显存紧张时，可选 Janus-Pro-1B：相比 Janus 1.5B，GenEval 从 0.61 升到 0.73，MMBench 从 69.4 升到 75.5，MMMU 从 30.5 升到 36.3（Table 3/4）。如果文生图指令遵循是核心指标，Janus-Pro-7B 在 Table 4 的统一模型中最高，明显优于 Show-o 的 0.53、Emu3-Gen 的 0.54 和前作 Janus 的 0.61。DPG-Bench 上，Janus-Pro-7B 的 84.19 也只比 SD3-Medium 低 0.11，比 DALL-E 3 低 0.69，考虑到分辨率只有 384，这个结果竞争力很强。

**不选 Janus-Pro 的情况**：只需要图像理解/QA，并且对 OCR 或文档细读要求很高。Janus-Pro 的输入分辨率固定 384×384，论文 §4 明确说这会影响精细 OCR 等任务。但论文没有直接对比高分辨率理解模型在 OCR 上的分数，因此这一条是作者自己声明的限制，缺少消融证据。需要高分辨率或高质量细节的纯生成时，Janus-Pro 输出固定 384×384，VQ 解码器的重建损失会导致小面部等细粒度区域欠细节（§4）。此时 SD3-Medium 等扩散模型在 DPG 上几乎持平，且通常面向更高的输出分辨率，更适合需要精细质感的场景。需要生成复杂空间关系或精确计数时，GenEval 的计数单项只有 0.59，说明仍有明显失败率（Table 4）。如果团队已有成熟的扩散模型管线，并且不需要统一理解，替换为 Janus-Pro 可能不会带来分辨率或细节上的收益。

简言之：如果目标是“一个模型、理解+生成、中等分辨率可接受”，Janus-Pro 是当前基准上的强候选；如果分辨率、OCR 或单项生成粒度是硬约束，应按对应基准选择专用模型，或者等待高分辨率版本。论文自己也把提高分辨率列为未来缓解方向（§4）。在统一模型类别内，Janus-Pro-7B 在理解基准上领先于 Show-o、Chameleon、VILA-U 等同参数量模型，但在某些指标上不如更大的 TokenFlow-XL 或 ILLUME，因此若只需要理解，不妨考虑更专注理解的高分辨率模型。

## 10. 工程判断：可行性、风险与上限

**数据**：理解预训练增加约 90M 样本，生成侧约 72M 合成美学数据。总量不小，但论文没有披露采集、清洗、去重、版权审查等工程细节。合成数据的 prompt 公开可用（§2.3，引用 [43]），但图像来源未详述。真实:合成的 1:1 比例只适用于统一预训练阶段 Stage II。复现成本主要集中在 Stage II 和 Stage III，需要同时处理多源理解数据和生成数据。如果团队没有现成的图像-文本对和合成数据管道，仅数据准备就可能成为瓶颈。约 90M 理解数据中包括 YFCC 和 Docmatix 等公开数据集，但清洗和格式统一需要额外工作。合成美学数据的生成方式（是否用其他模型生成）论文没有说明。

**算力/延迟**：训练使用 16/32 节点×8 张 A100 40GB，约 9/14 天（§3.1）。按照常见 A100 40GB 的租用成本估算，训练一次 Janus-Pro-7B 的成本在数万美元量级，但这是基于外部价格的推断，论文没有给成本数字。推理延迟和吞吐未披露。工程推断：7B 模型自回归生成 576 个图像 ID，每步经过 30 层 Transformer，比单步扩散模型迭代次数多，但单步计算更轻；如果不使用 KV cache、投机解码或批处理，生成一张图的可服务成本不低。7B 权重 FP16 约 14GB，单卡推理可行，但加上 KV cache 和激活会更高；1B 权重约 4GB，更易部署。训练框架是 HAI-LLM，基于 PyTorch（§3.1）。用户请求一张图可能需要数秒到数十秒，具体取决于硬件和实现，论文未提供数据。

**实现难点**：两个视觉编码器在不同阶段冻结/解锁容易出错，尤其 Stage III 只解锁理解编码器，生成编码器仍冻结。序列打包需要正确处理 attention mask，避免跨样本信息泄漏。多任务混合比例对性能敏感，Table 2 的三个阶段比例是调出来的结果，不是默认值。VQ tokenizer 与 LLM 隐空间的对齐依赖两层 MLP，容量有限；如果 adapter 容量不足，可能成为表征瓶颈。图像 ID 分布和文本 token 分布不同，可能导致采样失衡，尤其低频 ID 难以生成。输出分辨率 384×384 决定了模型无法直接生成高分辨率内容，再训练一个超分模块需要额外工作。Stage II 早停步数 270K 是经验值，可能无法直接迁移到不同数据规模。

**失败环节**：OCR 和小文本读取受输入分辨率限制（§4）；生成细节中小物体如面部区域因 VQ 重建损失而欠细节（§4）；GenEval 计数单项 0.59 说明复杂计数仍不可靠（Table 4）；短 prompt 稳定性有所改善，但 Figure 2 仍展示的是精选样本，不能保证所有短 prompt 都稳定。如果真实场景需要精确空间布局、长文本渲染、高分辨率产品图，Janus-Pro 可能不达标。此外，论文没有报告安全、版权、偏见评估，这些在生产部署中可能是失败点。模型生成的图像可能包含不当内容，其安全机制完全依赖底层 LLM 和训练数据的分布。

**监控信号**：论文未给训练曲线，但可以从任务性质推断监控指标。建议按阶段监控：理解样本的文本 token 交叉熵、生成样本的图像 ID 交叉熵；定期在 MMBench、GenEval、DPG-Bench 的小样本代理集上评估。如果 Stage I 生成损失不下降，说明 adapter 或图像头未充分对齐；如果 Stage II 生成损失震荡，可能是合成数据噪声或混合比例问题；如果 Stage III 理解指标不升，可能是 SigLIP 解锁过猛破坏预训练特征。这些是工程建议，不是论文内容。此外，可监控生成 ID 的熵，若过低说明采样塌缩，若过高说明不确定性大。

**指标上限**：理解受限于 384×384 输入和 SigLIP 的表示能力，复杂文档/图表细读难以突破；生成受限于 VQ tokenizer 的重建损失和离散 ID 信息瓶颈。即使继续扩大 LLM 到 13B、30B，上游编码器和分辨率仍是天花板。论文只验证到 7B，更高规模是否持续增益未知。GenEval 计数 0.59 和 DPG Global 86.90 可能就是当前 arch 在该分辨率下的暂时上限。除非更换更细粒度的 VQ 编码器、提高分辨率或引入混合架构，否则这些瓶颈难以通过简单加数据解决。

**未回答问题**：论文没有给出单一改动贡献消融；没有推理延迟/吞吐；没有采样策略；没有安全、版权、偏见评估；没有高分辨率方案；没有视频或多图扩展；没有损失曲线或数据效率曲线。同时，没有比较解耦编码与共享编码在相同 7B 规模下的因果差异。

## 11. 放回研究脉络并收束

研究脉络：统一多模态模型近年从“一个 Transformer 同时理解和生成”展开，代表如 Show-o、Emu3、Chameleon，大多共享视觉编码。Janus 提出解耦视觉编码来缓解理解/生成的表示冲突，在 1B 验证了可行性。Janus-Pro 把这一思路推进到数据与模型规模：修正训练三阶段，把 ImageNet 类别名生成从 Stage II 移到 Stage I，Stage II 专注密集描述；加入大规模理解和合成美学数据，扩展到 7B。它更像是“把解耦视觉编码放在更大算力和数据下重新检验”，贡献偏工程与实证。论文止步于 7B 和 384 分辨率，尚未触及高分辨率、视频、多图等。与同时期统一模型相比，Janus-Pro 在 GenEval 和 DPG-Bench 上第一，但在输入分辨率上明显落后于部分专用理解模型，这暗示解耦编码可以在小模型上换来生成优势，但理解上限仍受分辨率约束。

前作 Janus 的 Stage II 中 66.67% 文生图训练步用于 ImageNet，造成计算浪费；Janus-Pro 将 ImageNet 训练集中到 Stage I，并在 Stage II 完全放弃该数据，使密集描述训练步占比显著提高。同时，理解数据从 Janus 的未披露规模增加到约 90M，生成数据加入 72M 合成美学数据。这些改动共同使 7B 模型在多个基准上超越前作和部分专用模型。值得注意的是，Janus-Pro 并没有改变架构，因此它的上限仍是解耦编码 + 自回归离散 token 框架。

**读完必须记住的 5 件事**：

1. Janus-Pro 架构与 Janus 相同，不是新架构；改进集中在训练策略、数据、模型规模三点（§2）。训练策略上，Stage II 丢弃 ImageNet，Stage I 增加预热步数；数据上，理解约 90M、生成约 72M 合成数据；模型从 1.5B 扩到 7B。
2. 理解编码器和生成编码器完全分离：SigLIP 负责语义特征，VQ tokenizer 负责离散 ID，避免表示冲突（§2.1）。两个 adapter 均为两层 MLP，分别对齐到 LLM 输入空间。
3. 训练三阶段：Stage I 训适配器/图像头，Stage II 统一预训练并丢弃 ImageNet，Stage III 解锁理解编码器并调数据比例 5:1:4（§2.2, Table 2）。Stage II 计划 360K，实际 270K 早停。
4. 关键数据扩展：理解约 90M 样本，生成约 72M 合成美学数据，真实:合成 1:1；模型从 1.5B 到 7B（§2.3/2.4）。生成数据在 Stage II 中与密集描述配对，提升指令遵循和美学稳定性。
5. 实验结果：7B 在 MMBench 79.2、GenEval 0.80、DPG 84.19；但 384×384 分辨率限制 OCR 与细节，GenEval 计数单项仅 0.59（§3/4）。训练成本为 16/32 节点约 9/14 天。

**5 道自测题**：

1. Janus-Pro 在视觉理解与生成分别使用什么编码器？为什么不用同一个？
2. Stage II 为什么移除 ImageNet 数据？这项改动解决了原 Janus 的什么问题？
3. 训练数据中的“5:1:4”指什么？降低文生图比例后，哪些指标支持“不牺牲生成”的说法？
4. 如果用户主要做高分辨率文生图，Janus-Pro-7B 有哪些局限？请给出论文中两个具体证据。
5. 论文中哪些有关模型规模或数据贡献的结论没有被量化消融支持？

最终一句话总结：Janus-Pro 用更合理的训练流程、更大更干净的数据和更大的 LLM 证明了 Janus 的解耦视觉编码可以同时提升理解与生成，但它仍是 384 分辨率下的中端方案，离解决精细 OCR 和高细节生成还有距离。
